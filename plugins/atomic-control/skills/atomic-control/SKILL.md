---
name: atomic-control
description: Use Atomic Control to submit custom Atomic tests for review, discover approved tests and actors, request authorized validation or cleanup, and inspect execution evidence. Applies to this project's dashboard and MCP workflows, not direct shell execution of tests.
---

Use the bundled Atomic Control MCP tools for the requested outcome. The local plugin runs on a macOS or Linux Codex host; Windows/Linux execution actors are separate machines.

Use the authenticated HTTPS `atomic_control` MCP connection for real operations. When dashboard-link tools are installed, `atomic_dashboard_status` returns configured URLs and `atomic_dashboard_start` can open the dashboard with `open_browser=true` on request. They do not manage deployment processes. Missing tools require [connection setup](references/connection.md); do not substitute a shared identity, bypass authentication or execute tests directly through a shell.

For discovery, use `atomic_list_tests`, `atomic_get_test_details`, `atomic_list_actors` and `atomic_list_execution_profiles`. Retrieve exact GUIDs, actor UUIDs and provisioned profile UUIDs. Match supported platform, catalog revision, online health and the requested identity. Preserve the user's host, test and privilege choices; clarify a materially ambiguous target rather than guessing.

Submit authorized validation with `atomic_request_test`, prerequisite checks with `atomic_check_prerequisites`, and separately authorized cleanup with `atomic_cleanup_test`. Supply a stable unique idempotency key for each intended operation. Testing reasons are optional for execution, prerequisite checks and batches; include the user's reason when provided, without inventing one or prompting solely for it. Cleanup retains its required reason. Reuse that same key and arguments after a transport failure; never create a duplicate request merely because acknowledgement was lost. Prerequisite checks can execute reviewed dependency commands.

For user-requested custom tests, call `atomic_add_custom_test` with Atomic technique YAML, a stable idempotency key and optional base64 supporting files under `atomics/<technique>/`. A document can contain up to 100 tests. Each test needs a new GUID; submission cannot overwrite existing catalog definitions. The API creates unapproved entries with an immutable content revision, not a GitHub commit. Report returned GUIDs and leave approval to a human administrator in Test Catalog. Submission does not authorize execution. Retain the same key and exact inputs after transport failure. Missing supporting files can be supplied during review.

Respect the deployment's approval mode. In catalog mode, the administrator's definition approval is standing authorization for compatible enrolled hosts: an explicit operator request queues directly and returns `authorization_source: catalog`. Request it only for the user's selected test, actor and identity. In per-run mode, a `pending_approval` response awaits dashboard review, including separate privileged approval for root/administrator profiles. Neither acceptance nor a queued state is execution success. MCP has no approval, catalog-replacement or account-provisioning capability. Do not use shell/REST workarounds or substitute another identity to approve a request.

Use `atomic_get_execution` for actual state, identity evidence and logs. If asked to monitor, continue in the current task while execution progresses; human approval or unresolved reconciliation needs the user's dashboard action. Report the observed terminal result and distinguish process completion from detection coverage and artifact cleanup. Never relaunch an inconclusive execution automatically.


For a user-requested group of tests, collect the exact selected GUIDs (paginate discovery for “all matching” results), preserve their order and use one actor/profile. Call `atomic_preview_queue` first and report eligible/excluded counts and reasons. Submit the requested eligible selection with `atomic_queue_tests`, the returned preview hash and a stable idempotency key. A stale preview requires a new preview; do not silently broaden the selection. Use `atomic_get_queue` or `atomic_get_batch` for progress and `atomic_get_execution` for each test's evidence. When authorized, `atomic_control_batch` pauses, resumes or cancels remaining work; it lets the active execution finish. Review pause reasons before resuming and leave human reapproval/reconciliation to the dashboard. Batches expire after 24 hours by default; never silently resubmit expired work or automatically run cleanup/dependency installation.
